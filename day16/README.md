# day16 — подключение MCP

Установка, ключи и команда запуска — в [корневом README](../README.md).

День про протокол, а не про ассистента: [`day15`](../day15/README.md) со всеми его гейтами остаётся позади, здесь один запрос и один ответ. Появляются две новые роли — **MCP-сервер**, который объявляет инструменты, и **MCP-клиент**, который к нему подключается и эти инструменты получает. Между ними stdio и JSON-RPC, и обе роли лежат в этой папке: сервер запускается подпроцессом из клиента.

Задание просит показать, что соединение устанавливается и список инструментов возвращается. Это `python day16/client.py` — пятнадцать строк, никакой модели. Но список инструментов сам по себе ничего не доказывает, поэтому рядом стоит тумблер **MCP**: один и тот же вопрос уходит в модель с инструментами и без них, и разница видна в ответе, а не в панели.

## Почему клиент низкоуровневый

В SDK есть готовый `Client`, который делает всё то же самое одной строкой. Здесь взята пара `stdio_client` + `ClientSession`, и причина одна:

```python
init = await session.initialize()   # InitializeResult: имя сервера, версия протокола, capabilities
listed = await session.list_tools() # ListToolsResult
```

`initialize()` возвращает ответ сервера на рукопожатие, и это единственное место, где «соединение установлено» перестаёт быть словами. Высокоуровневый клиент делает тот же вызов внутри себя и наружу его не отдаёт — а показать требуется именно его.

Соединение живёт ровно один запрос. Подпроцесс поднимается при входе в `async with`, закрывается при выходе, и время рукопожатия меряется каждый раз заново: 300–500 мс на запуск интерпретатора и обмен двумя сообщениями. Держать сервер между запросами было бы быстрее, но тогда «подключились» нельзя было бы увидеть — только «подключились когда-то».

## Что говорит рукопожатие

```
$ python day16/client.py
Соединение установлено за 410 мс
  команда:     python server.py
  сервер:      AI Advent 16.0
  протокол:    2025-11-25
  возможности: experimental, prompts, resources, tools

Инструментов: 3

  list_days()
    Список итераций проекта: папка дня и чем этот день занят.

  day_task(day)
    Текст задания дня — то, что требовалось сделать, из его TASK.md.

  day_files(day)
    Из чего состоит день: файлы с размерами в байтах, без кэшей и баз.
```

Версию протокола сервер не выбирает сам: клиент присылает свою, сервер отвечает той, на которой они сойдутся, и `2025-11-25` в выдаче — результат переговоров, а не константа из кода. В `возможности` четыре пункта, хотя сервер объявляет только инструменты: `prompts` и `resources` есть у любого `MCPServer`, просто пустые.

## Инструменты про этот же репозиторий

Инструменты выбраны не абстрактные (`add(a, b)`) и это главное решение дня. Модель ничего не знает про этот проект, поэтому вопрос «что просят сделать в day13 и чем это отличается от day15» она без MCP не вытянет никак, а с MCP прочитает оба `TASK.md` и ответит точно. Разница между включённым и выключенным тумблером получается содержательной, а не косметической.

| Инструмент | Аргументы | Что отдаёт |
| --- | --- | --- |
| `list_days` | нет | папки `dayN` и название итерации из таблицы корневого README |
| `day_task` | `day` | текст `dayN/TASK.md` — что требовалось сделать |
| `day_files` | `day` | файлы дня с размерами, без `__pycache__` и `.db` |

Аргумент `day` принимает и `13`, и `day13`: модель зовёт инструмент и так, и так, а нормализация в одну строку дешевле, чем объяснение в описании.

Описания инструментов SDK берёт из docstring, а описания аргументов — из `Field`, а не из секции `Args`:

```python
Day = Annotated[str, Field(description="Номер или папка дня, например «13» или «day13».")]

@mcp.tool()
def day_task(day: Day) -> str:
    """Текст задания дня — то, что требовалось сделать, из его TASK.md."""
```

Если описать аргумент в docstring, он уедет в `description` инструмента целиком, вместе со словом `Args`, и продублирует схему, в которой уже всё есть. Схему `inputSchema` SDK собирает из аннотаций сам.

## Как инструмент MCP становится `tools` запроса

Перевод занимает шесть строк, потому что переводить почти нечего:

```python
{
    "type": "function",
    "function": {
        "name": tool.name,
        "description": tool.description,
        "parameters": tool.input_schema,   # один в один
    },
}
```

`inputSchema` инструмента MCP и `parameters` функции в запросе к модели — один и тот же JSON Schema, и это не совпадение: обе спецификации описывают аргументы одинаково. Так что MCP здесь не «ещё один формат инструментов», а способ получить их от чужого процесса, не зная заранее, какие они.

## Цикл хода

```mermaid
flowchart TD
    ask["запрос пользователя"] --> onoff{"тумблер MCP"}
    onoff -->|"выключен"| plain["стрим без tools: сервер не поднимается вовсе"]
    onoff -->|"включён"| conn["connect(): подпроцесс, initialize, list_tools"]
    conn --> frame["кадр mcp: сервер, протокол, инструменты, время"]
    frame --> call["стрим с tools"]
    call --> decide{"finish_reason"}
    decide -->|"tool_calls"| run["session.call_tool по каждому вызову"]
    run --> toolframe["кадр tool: имя, аргументы, результат, время"]
    toolframe --> call
    decide -->|"stop"| done["кадр done: раундов, вызовов, finish_reason"]
    plain --> done
```

Выключенный тумблер не поднимает сервер вообще. Это принципиально: «выключен» должно значить «сервера нет», иначе замер сравнивал бы не MCP с его отсутствием, а «модель видит инструменты» с «модель их не видит при живом соединении» — другой вопрос.

Системный промпт, температура и лимит у обоих режимов одни и те же. В промпте есть строка «не выдумывай содержимое файлов и заданий: если не знаешь, так и скажи» — она тоже общая, и без неё замер мерил бы не пользу инструментов, а склонность модели фантазировать.

Раундов не больше четырёх. Модель вправе сходить за данными несколько раз — в прогоне ниже она делает это дважды подряд, — но упереться в потолок должна кадром `done` с честным `finish_reason: max_rounds`, а не бесконечным хождением.

**Вызовы приходят кусками.** В потоке `delta.tool_calls` приезжают по частям: `id` и имя функции в первой дельте, аргументы — строкой по символам. Собирает их обратно `llm.py`, по `index`, и отдаёт готовыми вместе с `finish_reason`. Это единственное отличие `llm.py` этого дня от прошлых.

## Ошибка инструмента — это тоже ответ

Отказ внутри инструмента поднимается как `ToolError`, а не `ValueError`, и разница видна модели:

| Исключение | Что получает модель | Что в логе сервера |
| --- | --- | --- |
| `ValueError` | `Error executing tool day_task` | traceback на уровне ERROR |
| `ToolError` | `Error executing tool day_task: Папки day99 в проекте нет.` | строка на уровне INFO |

Первый вариант — крах, о котором клиенту знать не положено, и текст исключения из него намеренно вырезан. Второй — предусмотренный отказ, и причина доезжает до модели текстом. Разница не теоретическая: на вопрос про несуществующий day99 модель с `ToolError` отвечает «папки day99 в проекте нет, посмотреть список можно через `list_days`», то есть пользуется текстом ошибки как данными.

Аргументы, которые не разобрались как JSON, и вызов несуществующего инструмента обрабатываются там же и так же — возвращаются модели текстом в `role="tool"`. Ход на исправление у неё есть, и в ленте он виден.

## Прогон: один вопрос с MCP и без

> **Что просят сделать в day13 и чем это отличается от day15?**

*MCP включён — соединение 513 мс, 2 вызова, 2 раунда, `stop`:*

> **Day 13 — Task State Machine.** Нужно ввести у задачи формализованное состояние: этап, текущий шаг, ожидаемое действие. Пример цепочки: planning → execution → validation → done. Результат — агент с формализованным состоянием задачи.
>
> **Day 15 — Контролируемые переходы состояний.** Нужно сделать переходы между состояниями явными: список допустимых состояний, список разрешённых переходов, запрет «перепрыгивания» этапов (нельзя реализацию до утверждённого плана, нельзя финал без валидации). Результат — ассистент с контролируемым жизненным циклом задачи.
>
> **Разница:** day13 — это *описание* состояния (что у задачи есть этап/шаг/ожидаемое действие), day15 — *правила перехода* между состояниями (какие переходы разрешены и запрет пропуска этапов). То есть 15 строится поверх модели из 13.

*MCP выключен — 0 вызовов, 1 раунд, `stop`:*

> В репозитории AI Advent я не вижу подтверждённого содержимого папок `day13` и `day15`, поэтому не могу сказать, что именно в них просят сделать и чем задания отличаются. Чтобы ответить точно, нужно посмотреть файлы этих папок (например, README или инструкции внутри).

Ответ без MCP — правильный, и это важнее, чем если бы он был выдуманным. Модель не знает содержимого репозитория и говорит об этом прямо, потому что промпт её об этом просил. Разница между режимами поэтому измеряется не «правда против вымысла», а «ответ против отказа»: инструменты дают не стиль и не рассуждение, а единственное, чего у модели нет, — данные.

Ещё два прогона, чтобы было видно остальные ветки:

| Вопрос | Вызовы | Раунды | Чем интересен |
| --- | --- | --- | --- |
| Сколько всего дней в проекте и из скольких файлов состоит последний? | `list_days()`, затем `day_files(day16)` | 3 | второй вызов зависит от результата первого: модель сначала узнаёт, какой день последний |
| Расскажи, что просят сделать в day99 | `day_task(99)` → ошибка | 2 | отказ инструмента модель прочитала и пересказала, а не проигнорировала |

Первый из них показал и побочное: про day16 инструмент вернул пустое название, и модель это заметила — «у day16 в списке пустое название, так что чем занят этот день — не знаю». Строки про этот день в таблице корневого README тогда ещё не было.

## Интерфейс

Тумблер `MCP` стоит слева в строке действий, рядом с кнопкой. Под формой — панель **Соединение**: при включённом тумблере в ней рукопожатие (команда запуска, сервер, протокол, возможности) и карточки инструментов с аргументами и описаниями, при выключенном — строка «MCP выключен: инструментов у модели нет, отвечает по памяти». Кнопка «Проверить соединение» поднимает сервер без модели и заполняет ту же панель: это задание в чистом виде, одним нажатием.

Панель **Вызовы инструментов** появляется, только если вызовы были, и растёт по ходу ответа: имя с аргументами, время и результат целиком. Неудачный вызов подсвечен красным. Под ответом — раунды, число вызовов и `finish_reason`.

## API

| Метод | Путь | Зачем |
| --- | --- | --- |
| `POST` | `/api/connect` | только соединение и список инструментов, без модели |
| `POST` | `/api/ask` | `{"prompt": "...", "mcp": true}` — ход целиком потоком |

Кадры SSE в `/api/ask`: `mcp` — рукопожатие и инструменты (только при включённом тумблере), безымянные кадры — куски ответа, `tool` — вызов инструмента с аргументами, результатом и временем, `done` — итог хода, `error` — ошибка вместо ответа.
