# AI Advent

Итерации проекта по дням, каждая в своей папке.

| Папка | Итерация |
| --- | --- |
| `day1/` | CLI: запрос из терминала, потоковый вывод в stdout |
| `day2/` | Веб-интерфейс: сравнение свободного ответа и ответа по ограничениям из JSON |
| `day3/` | Веб-интерфейс: одна задача, один запрос — способы рассуждения из чекбоксов |
| `day4/` | Веб-интерфейс: один запрос, температура задаётся слайдером |
| `day5/` | Веб-интерфейс: один запрос уходит в три модели разной силы, замеры времени, токенов и стоимости |
| `day6/` | Веб-чат: агент с памятью диалога — отдельная сущность, инкапсулирующая промпт, историю и вызов LLM |
| `day7/` | Веб-чат: история диалогов в SQLite — переписка переживает перезапуск процесса, диалогов может быть несколько |
| `day8/` | Веб-чат: подсчёт токенов запроса, истории и ответа, бюджет контекста в токенах, стоимость по ходам |
| `day9/` | Веб-чат: сжатие истории — последние сообщения дословно, остальное конспектом, который агент пишет себе сам |

## Установка

Общее виртуальное окружение в корне, зависимости — под конкретный день:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r day2/requirements.txt
```

Зависимости `day2`–`day7` совпадают, в `day8` и `day9` к ним добавляется `tiktoken` — им считаются токены до отправки запроса.

## Настройка

Скопируйте `.env.example` в `.env` и укажите ключи:

```
DEEPSEEK_API_KEY=sk-xxxxxxxxxxxxxxxx
DEEPSEEK_MODEL=deepseek-v4-flash
OPENROUTER_API_KEY=sk-or-v1-xxxxxxxxxxxxxxxx
```

`.env` лежит в корне и подхватывается из папок day1–day9. `DEEPSEEK_MODEL` необязателен и читается в `day2`–`day4` и `day6`–`day9`, по умолчанию используется `deepseek-v4-flash`; в `day1` модель задана в коде, в `day5` — список моделей.

`OPENROUTER_API_KEY` нужен только в `day5`: слабая модель берётся из OpenRouter, потому что DeepSeek API отдаёт всего два уровня — `deepseek-v4-flash` и `deepseek-v4-pro`.

## day2 — ограничения формата ответа

```bash
uvicorn main:app --reload --app-dir day2
```

Интерфейс доступен на http://127.0.0.1:8000

Один промпт уходит в модель дважды: без ограничений и с ограничениями из `day2/constraints.json`. Обе колонки показывают количество слов и `finish_reason`, чтобы разницу было видно.

Ограничения правятся только в файле, без изменений кода:

```json
{
  "system_prompt": "You are a helpful assistant.",
  "sections": [
    {
      "title": "Формат ответа",
      "rules": [
        "Используй ровно 3 пункта.",
        "Каждый пункт должен содержать одно предложение.",
        "Используй формат нумерованного списка: 1., 2., 3."
      ]
    }
  ],
  "params": { "max_tokens": 200, "stop": ["4."] }
}
```

`system_prompt` и `sections` собираются в system prompt, `params` уходят в `chat.completions.create` как есть. `stop: ["4."]` обрывает генерацию, если модель всё же начнёт четвёртый пункт.

| Файл | Назначение |
| --- | --- |
| `day2/main.py` | FastAPI-приложение, роуты `/`, `GET /api/constraints`, `POST /api/ask` |
| `day2/llm.py` | Клиент DeepSeek, стрим чанков |
| `day2/constraints.json` | Ограничения: формат, длина, условие завершения, параметры API |
| `day2/constraints.py` | Pydantic-модели ограничений и сборка system prompt |
| `day2/static/` | Страница интерфейса: HTML, CSS, JS |

### API

`POST /api/ask` принимает `{"prompt": "...", "constrained": false}` и отдаёт `text/event-stream`: кадры `data: <json-строка>` с частями ответа, затем `event: done` с `{finish_reason, word_count}` либо `event: error` с текстом ошибки. При `constrained: true` применяются ограничения из файла.

`GET /api/constraints` возвращает содержимое `constraints.json` — интерфейс рисует из него блок ограничений.

## day3 — способы рассуждения

```bash
uvicorn main:app --reload --app-dir day3
```

Интерфейс доступен на http://127.0.0.1:8000

Один запрос: без чекбоксов это прямой ответ, включённые опции складываются в один промпт.

| Чекбокс | Что происходит |
| --- | --- |
| Решай пошагово | В system prompt добавляется «Решай пошагово» |
| Сначала промпт | Модель сначала составляет промпт, затем отвечает по нему |
| Группа экспертов | В запрос добавляется список ролей (по умолчанию аналитик, инженер, критик) |

| Файл | Назначение |
| --- | --- |
| `day3/main.py` | FastAPI-приложение, роуты `/`, `GET /api/defaults`, `POST /api/ask` |
| `day3/llm.py` | Клиент DeepSeek, задача и роли по умолчанию, сборка system prompt, стрим чанков |
| `day3/static/` | Страница интерфейса: HTML, CSS, JS |

### API

`POST /api/ask` принимает `{"prompt": "...", "step_by_step": false, "meta_prompt": false, "experts": []}` и отдаёт `text/event-stream`: кадры `data: <json-строка>` с частями ответа, затем `event: done` с `{finish_reason, word_count}` либо `event: error` с текстом ошибки.

Пустой `experts` — эксперты выключены. Задача и роли по умолчанию задаются в `day3/llm.py` (`DEFAULT_PROMPT`, `DEFAULT_EXPERTS`) и отдаются через `GET /api/defaults`. Если `meta_prompt: true`, перед чанками ответа приходит `event: stage` со значением `"prompt"` или `"answer"`: сначала стримится сгенерированный промпт, затем решение.

## day4 — температура

```bash
uvicorn main:app --reload --app-dir day4
```

Интерфейс доступен на http://127.0.0.1:8000

Страница состоит из поля ввода, слайдера температуры, кнопки и одного блока ответа. Слайдер идёт от `0` до `2` с шагом `0.1`, рядом числовое поле — они синхронизированы, значение вне диапазона клампится, дробное подгоняется под шаг. Значение по умолчанию — `0.7`. После ответа в шапке блока выводится использованная температура и количество слов.

Сравнение делается вручную: один и тот же промпт отправляется с разными положениями слайдера. Подпись под слайдером меняется по значению:

| Диапазон | Подпись |
| --- | --- |
| 0.0–0.2 | Максимально детерминированно: факты, код, классификация |
| 0.3–0.6 | Баланс точности и разнообразия; хороший default для большинства задач |
| 0.7–1.0 | Более творческие и разнообразные ответы |
| 1.1–1.4 | Высокая вариативность, больше неожиданных формулировок |
| 1.5–2.0 | Очень высокая случайность; выше риск бессвязности и ошибок |

Границы и шаг слайдера (`TEMP_MIN`, `TEMP_MAX`, `TEMP_STEP`), значение по умолчанию (`DEFAULT_TEMPERATURE`) и тексты диапазонов (`TEMPERATURE_BANDS`) заданы в `day4/llm.py` и приходят на страницу через `GET /api/defaults`. Своих значений страница не хранит: до ответа `/api/defaults` слайдер, числовое поле и кнопка выключены — шкала правится в одном месте.

### Выводы по температуре

Замеры на дефолтном промпте: по три генерации на каждое значение, разнообразие — средняя мера Жаккара по множествам слов между парами ответов (чем ниже схожесть, тем сильнее ответы разошлись).

| Настройка | Точность | Креативность | Разнообразие | Для каких задач |
| --- | --- | --- | --- | --- |
| `0` | Максимальная: модель берёт самый вероятный токен, состав и порядок мыслей стабильны | Минимальная: формулировки шаблонные, аналогии предсказуемые | Низкое: схожесть повторных запусков `61%`, отличия в отдельных формулировках | Извлечение фактов, классификация, разбор JSON, генерация и рефакторинг кода, SQL, тесты и всё, что нужно повторить и сравнить |
| `0.7` | Высокая, но факты уже формулируются по-разному | Заметная: появляются живые примеры и небанальные аналогии | Среднее: схожесть `26%`, структура ответа сохраняется | Объяснения, документация, ответы поддержки, черновики текстов — рабочий default для большинства задач |
| `1.2` | Ниже: растёт риск неточностей и вольных утверждений, ответ надо проверять | Высокая: неожиданные метафоры, редкие слова, нестандартные ходы | Большое: схожесть `19%`, каждый запуск — отдельный вариант | Брейншторм, нейминг, слоганы, сюжеты, генерация набора идей, из которых потом выбирают вручную |

Практическое правило: чем важнее правильность и воспроизводимость, тем ниже температура; чем важнее набор непохожих вариантов, тем выше. Выше `1.5` ответы становятся нестабильными — модель начинает терять связность, поэтому такой режим полезен разве что для генерации сырых идей.

Побитовой воспроизводимости при `temperature = 0` нет даже у одного и того же промпта: API не гарантирует детерминизм, поэтому ответы совпадают по смыслу и структуре, но расходятся в отдельных формулировках.

| Файл | Назначение |
| --- | --- |
| `day4/main.py` | FastAPI-приложение, роуты `/`, `GET /api/defaults`, `POST /api/ask` |
| `day4/llm.py` | Клиент DeepSeek, шкала температур, запрос по умолчанию, стрим чанков |
| `day4/static/` | Страница интерфейса: HTML, CSS, JS |

### API

`POST /api/ask` принимает `{"prompt": "...", "temperature": 0.7}` и отдаёт `text/event-stream`: кадры `data: <json-строка>` с частями ответа, затем `event: done` с `{finish_reason, word_count}` либо `event: error` с текстом ошибки. `temperature` вне диапазона `0…2` — ответ `422`.

`GET /api/defaults` возвращает запрос по умолчанию, стартовую температуру, границы слайдера и подписи диапазонов.

## day5 — версии моделей

```bash
uvicorn main:app --reload --app-dir day5
```

Интерфейс доступен на http://127.0.0.1:8000

Один промпт уходит одновременно в три модели разной силы. Колонки строятся по ответу `GET /api/models`, в шапке каждой автоматически появляются время, токены и стоимость — считать вручную ничего не нужно.

### Модели

| Уровень | Модель | Провайдер | Ссылка |
| --- | --- | --- | --- |
| Слабая | `cohere/north-mini-code:free` | OpenRouter | [openrouter.ai/cohere/north-mini-code:free](https://openrouter.ai/cohere/north-mini-code:free) |
| Средняя | `deepseek-v4-flash` | DeepSeek | [api-docs.deepseek.com](https://api-docs.deepseek.com/quick_start/pricing) |
| Сильная | `deepseek-v4-pro` | DeepSeek | [api-docs.deepseek.com](https://api-docs.deepseek.com/quick_start/pricing) |

Слабая модель взята из OpenRouter: DeepSeek API отдаёт только flash и pro. Это разреженная MoE на 30B параметров, из которых на токен работают 3B — против моделей DeepSeek она и есть слабый уровень. Условия запроса одинаковые для всех трёх — `temperature = 0.3`, `max_tokens = 4000`, один и тот же system prompt; у обеих моделей DeepSeek мышление выключено, чтобы сравнивать сами модели, а не режимы работы.

Выбор бесплатной модели упирается не только в качество. Кандидаты помельче либо не доводят ответ до конца, либо недоступны: `liquid/lfm-2.5-2.6b:free` тратит на обязательное рассуждение больше, чем весь бюджет, и до ответа не доходит; `nvidia/nemotron-3.5-lightning:free` упирается в тот же лимит на 4491 токене рассуждения; у Gemma 4 (`26b-a4b` и `31b`) общий бесплатный пул отдаёт один запрос и дальше уходит в `429`. `cohere/north-mini-code:free` отвечал во всех проверках и укладывался в бюджет, поэтому стоит он.

### Как считаются метрики

Токены приходят в самом стриме: `stream_options: {"include_usage": true}` добавляет `usage` в последний чанк, так что отдельный запрос за статистикой не нужен.

Стоимость не оценивается, а берётся точной. OpenRouter при `usage: {"include": true}` возвращает готовое `usage.cost`. Для DeepSeek она считается по `prompt_cache_hit_tokens`, `prompt_cache_miss_tokens` и `completion_tokens` по прайсу из `day5/llm.py`, с поправкой на время суток: пик — 01:00–04:00 и 06:00–10:00 UTC в пн–пт, в остальные часы цены вдвое ниже.

Время до первого токена считается двумя числами. Слабая модель часть бюджета тратит на рассуждение, и приходит оно отдельным полем `reasoning`, а не `content`. Если мерить только по первому куску ответа, модель выглядит мертвее, чем есть: поток уже идёт, просто не тот. Поэтому отдельно замеряется первый токен любого типа и первый токен собственно ответа — разница между ними и есть время на размышления.

Пока идёт рассуждение, в шапке колонки стоит «рассуждает...», а сам текст рассуждения не показывается — его объём виден в метриках. Но модель может уйти в рассуждение целиком и до ответа не дойти, поэтому колонка не остаётся с плейсхолдером: по `event: done` она сообщает, что ответа нет и весь лимит `max_tokens` съело рассуждение, и выводит это рассуждение, чтобы было видно, на что ушли токены. Если ответ есть, но обрезан по лимиту, под ним появляется отметка об обрезке — `finish_reason: length` не должен выглядеть как нормальное завершение.

### Замеры

Дефолтный промпт — классическая задача про 12 монет и 3 взвешивания (нужно назвать фальшивую монету и сказать, тяжелее она или легче). Три прогона, в таблице медианы. Тарифы непиковые.

| Метрика | Слабая | Средняя | Сильная |
| --- | --- | --- | --- |
| Первый токен | 0.5 с | 0.7 с | 1.2 с |
| Первый токен ответа | 2.3 с | 0.7 с | 1.2 с |
| Всего | 49.8 с | 8.1 с | 11.8 с |
| Токены входа | 70 | 80 | 80 |
| Токены ответа | 3059 | 1567 | 1142 |
| Из них рассуждение | 67 | 0 | 0 |
| Скорость генерации | 56.2 ток/с | 198.1 ток/с | 103.3 ток/с |
| Стоимость запроса | $0 (бесплатная) | $0.001052 | $0.002314 |

### Выводы

Все три модели доводят решение до конца (`finish_reason: stop`) во всех прогонах, но цена этой полноты разная.

Слабая модель самая медленная и самая многословная: медиана 49.8 с и 3059 токенов ответа против 8.1 с / 1567 у средней. Собственно ответ начинается только на 2.3 с — первые куски уходят в короткое рассуждение. Генерирует она 56 ток/с, в 3.5 раза медленнее средней, и разброс между прогонами большой (41–59 с). Бесплатность обманчива: если посчитать её токены по тарифу flash, запрос вышел бы около $0.0020 — почти как сильная модель, при этом ждать приходится вчетверо дольше.

Средняя модель — лучшая по скорости: 8.1 с, 198 ток/с, стоимость $0.001052. Даёт полное дерево случаев 4-на-4, но длиннее, чем нужно: 1567 токенов против 1142 у сильной.

Сильная модель короче всех (1142 токена) и стабильнее по длине ответа между прогонами, но дороже средней в 2.2 раза и медленнее её (11.8 с против 8.1 с) — крупная модель отдаёт токены вдвое медленнее. Оправдана, когда важны краткость и предсказуемый объём; на этой задаче средняя выигрывает по времени и деньгам при том же полном решении.

Практическое правило: на длинных рассуждениях бесплатная «слабая» модель съедает больше всего времени и токенов; средняя даёт рабочий полный ответ быстрее и дешевле сильной; сильная экономит на объёме, но не на времени.

Отдельно про бесплатный тариф: пул у него общий, и на серии запросов провайдер отдаёт `429` (`limit_source: upstream_provider_shared_pool`). Штатный фолбэк OpenRouter через список `models` от такой ошибки не спасает — проверено. Поэтому замеры прогонялись последовательно, а колонка при отказе показывает ошибку, не мешая двум остальным ответить.

| Файл | Назначение |
| --- | --- |
| `day5/main.py` | FastAPI-приложение, роуты `/`, `GET /api/models`, `POST /api/ask` |
| `day5/llm.py` | Реестр трёх моделей, клиенты провайдеров, прайс и расчёт стоимости, стрим со сбором метрик |
| `day5/static/` | Страница интерфейса: HTML, CSS, JS |

### API

`GET /api/models` возвращает запрос по умолчанию, `temperature`, `max_tokens`, признак пиковых тарифов и список моделей: ключ, уровень, id, провайдер, ссылки и платная ли модель. Своих значений страница не хранит — колонки рисуются из этого ответа.

`POST /api/ask` принимает `{"prompt": "..."}` и отдаёт один `text/event-stream` на все три модели. Запросы стартуют одновременно от общей точки отсчёта и пишут в общую очередь — при трёх отдельных запросах из браузера точки отсчёта разъезжаются и сравнение времени становится нечестным.

| Кадр | Содержимое |
| --- | --- |
| `event: chunk` | `{"model", "kind", "text"}`, где `kind` — `reasoning` или `answer` |
| `event: done` | метрики модели: время, токены, скорость, стоимость, `finish_reason` |
| `event: error` | `{"model", "message"}` — ошибка одной модели не роняет остальные |
| `event: end` | все три модели закончили |

## day6 — агент с памятью диалога

```bash
uvicorn main:app --reload --app-dir day6
```

Интерфейс доступен на http://127.0.0.1:8000

Веб-чат: сообщения идут лентой, ответ агента дописывается в последний пузырь по мере стрима. Пока первый токен не пришёл, в пузыре пульсируют три точки — ожидание видно сразу, а не после первых слов. В шапке — параметры агента (модель, `temperature`, лимит ответа), счётчик сообщений в памяти и кнопка «Новый диалог». `Enter` отправляет сообщение, `Shift + Enter` переносит строку; пока идёт ответ, `Enter` ничего не делает — остановка остаётся кликом по кнопке.

### Агент как сущность

До этого дня роут сам собирал сообщения для модели. Здесь между роутом и API появляется класс `Agent` из `day6/agent.py`, и вся логика разговора живёт в нём:

- system prompt, `temperature` и `max_tokens` — поля агента, а не аргументы запроса;
- история диалога — приватный список внутри агента, наружу отдаётся только `transcript()` и размер;
- `ask(prompt)` собирает контекст, дёргает модель и отдаёт поток `AgentDelta`.

`day6/llm.py` после этого знает только про транспорт: `stream_chat(messages, temperature, max_tokens)` отправляет готовый список сообщений и стримит чанки. Роут `POST /api/ask` не строит промпт и не хранит переписку — он берёт агента по `session_id`, вызывает `ask()` и перекладывает дельты в SSE. Заменить модель, промпт или политику памяти можно, не трогая ни роуты, ни страницу.

Память живёт в процессе: `AgentRegistry` в `day6/main.py` держит `session_id → Agent` и вытесняет самую старую сессию после сотой. Браузер хранит только `session_id` в `localStorage`, поэтому после перезагрузки страницы лента восстанавливается запросом истории у агента — переписка принадлежит серверу, а не вкладке.

Контекст ограничен: `HISTORY_LIMIT = 20` сообщений, то есть 10 ходов. Обрезка идёт с начала и следит, чтобы диалог не начинался с ответа ассистента — иначе первой в контексте окажется реплика на вопрос, которого модель уже не видит. Отдельный ответ ограничен `MAX_TOKENS = 2000`: если модель упрётся в потолок, приходит `finish_reason: length` и под полем ввода появляется отметка об обрезке.

Ход попадает в память только целиком. Если стрим оборвался — ошибка API или пользователь нажал «Остановить», — в историю не уходит ни вопрос, ни обрывок ответа, и страница убирает эту пару из ленты, возвращая текст в поле ввода. Иначе на экране остались бы сообщения, которых агент не помнит. Параллельные запросы в одну сессию сериализуются `asyncio.Lock`, чтобы два хода не собирали контекст одновременно.

### Проверка памяти

```bash

curl -sN -X POST http://127.0.0.1:8000/api/ask -H 'Content-Type: application/json' \
```

Второй запрос не содержит ни имени, ни языка, но агент отвечает «Тебя зовут Игорь, а твой любимый язык — Python»: контекст подставил он сам. В интерфейсе то же самое видно по счётчику — после каждого хода в памяти становится на два сообщения больше.

| Роут | Назначение |
| --- | --- |
| `GET /api/defaults` | system prompt, запрос по умолчанию, `model`, `temperature`, `max_tokens`, `history_limit` |

## day7 — постоянная память

```bash
uvicorn main:app --reload --app-dir day7
```

Интерфейс доступен на http://127.0.0.1:8000

Тот же чат, что в `day6`, но переписка живёт не в процессе. В `day6` память была списком внутри объекта `Agent`: `Ctrl+C` по uvicorn — и диалога нет, `session_id` в `localStorage` остаётся, а сервер на него отвечает `404`. Здесь источник истины — SQLite-файл `day7/history.db`, и после перезапуска разговор продолжается с той же реплики. Раз диалоги переживают процесс, их стало несколько: слева панель со всеми сессиями из базы, между ними можно переключаться.

### Хранилище

База создаётся при старте приложения, схема — две таблицы:

```sql
CREATE TABLE sessions (
    id         TEXT PRIMARY KEY,
    title      TEXT,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE messages (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id TEXT NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
    role       TEXT NOT NULL,
    content    TEXT NOT NULL,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

Порядок сообщений задаёт `id`, а не время: `created_at` с точностью до секунды не различает вопрос и ответ внутри одного хода. Индекс по `(session_id, id)` обслуживает оба запроса — и всю ленту, и хвост для контекста.

`sqlite3` блокирующий, поэтому каждый вызов уходит в `asyncio.to_thread` и не занимает event loop. Соединение открывается на операцию: делить одно между потоками — значит возиться с `check_same_thread` и собственной блокировкой, а выигрыш на локальном файле нулевой. База в режиме WAL, так что запись хода не блокирует чтение ленты.

### Вся история и окно контекста

Это разные вещи, и в `day7` они разъезжаются:

- в базе лежит **весь** диалог — из него страница восстанавливает ленту целиком;
- в модель уходит **последние `HISTORY_LIMIT = 20` сообщений** — окно, которое агент держит в памяти процесса.

Счётчик в шапке показывает оба числа: «в диалоге 60 сообщений, в контексте 20 из 20». Обрезка окна осталась из `day6` вместе с правилом «контекст не начинается с ответа ассистента», но теперь она применяется и к хвосту, поднятому из базы: первым сообщением там тоже может оказаться ответ на вопрос, который в окно уже не попал.

### Агент и сессии

`Agent` больше не владеет памятью, а привязан к строке в `sessions`. Объект создаётся пустым и подтягивает хвост из базы при первом же ходе — ленивая загрузка избавляет от асинхронного конструктора. Записывается ход одной транзакцией и только целиком: оборванный стрим (ошибка API или «Остановить») не оставляет в базе ни вопроса, ни полуответа — как и в `day6`.

`AgentRegistry` из реестра памяти превратился в кэш живых объектов. `get(session_id)` отдаёт агента из словаря, а если его там нет — проверяет сессию в базе и собирает агента заново вокруг той же строки. `404` теперь означает «такой сессии не было», а не «сервер её забыл». Вытеснение сотой сессии перестало быть потерей данных: освобождается объект, переписка остаётся в файле.

### Список диалогов

Боковая панель показывает все сессии из базы: кнопка «Новый диалог» заводит ещё одну, клик по строке открывает её ленту, крестик удаляет вместе с перепиской (`ON DELETE CASCADE`) и выбрасывает агента из кэша. `list_sessions()` собирает панель одним запросом:

```sql
SELECT s.id,
       count(m.id) AS size,
       coalesce(s.title,
                (SELECT substr(content, 1, 80) FROM messages
                  WHERE session_id = s.id AND role = 'user'
                  ORDER BY id LIMIT 1)) AS title,
       coalesce(max(m.created_at), s.created_at) AS updated_at
FROM sessions s LEFT JOIN messages m ON m.session_id = s.id
GROUP BY s.id
ORDER BY updated_at DESC, s.rowid DESC
```

У пустой сессии сообщений нет, поэтому `coalesce` подставляет время её создания — иначе только что заведённый диалог уехал бы в конец списка. Секундной точности `created_at` не хватает, чтобы развести ходы внутри одной секунды, и порядок добирается из `rowid`.

### Заголовок диалога

В строке списка стоит не начало первого вопроса, а его суть: «Идемпотентность в HTTP» вместо «Объясни в трёх предложениях, что так...». Формулирует её сама модель — отдельным коротким запросом с собственным промптом (`TITLE_PROMPT` в `day7/agent.py`), `temperature = 0.2` и лимитом в 32 токена: заголовок это ярлык, а не ответ, и одна и та же тема не должна называться каждый раз по-новому.

Ждать его пользователю не приходится. Запрос уходит `asyncio.create_task` в момент первого хода и работает всё время, пока стримится ответ, — к `event: done` заголовок уже записан, и обычное обновление панели после хода подхватывает его вместе с новым порядком строк. Не-стримовый вызов для этого добавлен в `day7/llm.py` рядом со `stream_chat`: стримить нечего, когда ждут пару слов.

Имя даётся один раз, по первому вопросу, и дальше не меняется. Оборванный ход отменяет и задачу с заголовком: в базе не осталось ни вопроса, ни ответа, называть нечего. Сбой самого title-запроса ход не роняет — `s.title` остаётся `NULL`, и `coalesce` возвращает панель к началу первого вопроса. Тот же фолбэк работает для диалогов из базы, заведённой до появления колонки: `CREATE TABLE IF NOT EXISTS` существующую таблицу не трогает, поэтому `title` добавляется при старте отдельным `ALTER TABLE`.

Кнопка «Новый диалог» на пустом диалоге ничего не делает: заводить вторую пустую сессию незачем. Удаление открытого диалога открывает соседний, а на опустевшем списке сразу создаёт новый — странице всегда нужна живая сессия. На время стрима панель гаснет: уход в другой диалог посреди ответа увёл бы его в чужую ленту.

## day8 — токены и стоимость

```bash
uvicorn main:app --reload --app-dir day8
```

Интерфейс доступен на http://127.0.0.1:8000

Тот же чат, что в `day7`, но у каждого хода появился ценник. Под лентой — таблица: сколько токенов стоил запрос, сколько из них попало в кэш, сколько занял ответ, во что обошёлся ход и сколько диалог съел с начала. В шапке к параметрам агента добавились три счётчика (диалог, контекст, потрачено) и переключатель бюджета контекста.

### Три числа на каждый ход

| Число | Откуда | Когда известно |
| --- | --- | --- |
| Токены текущего запроса | system prompt + окно истории + новый вопрос | до отправки, кадр `event: prompt` |
| Токены всей истории диалога | все сообщения сессии из SQLite | до отправки, там же |
| Токены ответа | `usage.completion_tokens` | после ответа, кадр `event: done` |

Первые два считает сам агент — иначе стоимость запроса стала бы известна только после того, как за него заплатили. Третье приходит от модели: `stream_options: {"include_usage": true}` добавляет `usage` в последний чанк стрима, отдельный запрос за статистикой не нужен.

### Оценка до запроса и факт после

Токенизатор DeepSeek библиотекой не отдаёт, поэтому локальный счёт — это оценка на `cl100k_base` из `tiktoken`: словарь сопоставимого размера, но не тот же самый. К содержимому сообщений добавляются накладные расходы формата чата — `MESSAGE_OVERHEAD = 4` на сообщение и `REPLY_OVERHEAD = 3` на затравку ответа: голый текст занижает оценку ровно на длину разметки.

Расхождение не прячется, а показывается в таблице рядом с фактом:

| Текст | Оценка `cl100k_base` | Факт из `usage` | Расхождение |
| --- | --- | --- | --- |
| Русский, первый ход короткого диалога | 139 | 104 | +33.7% |
| Русский, 20 ходов подряд | 139…3840 | 104…3006 | +26.5…+40.5% |
| Латиница, блок из калибровки | 30 | 30.02 | −0.1% |

Вывод простой: на латинице `cl100k_base` совпадает с DeepSeek с точностью до десятых процента, а на русском завышает примерно на треть. Для бюджета это означает запас в свою пользу — агент обрезает историю раньше, чем этого потребовала бы модель, — но планировать по такой оценке деньги нельзя, для денег есть `usage`.

### Бюджет контекста вместо лимита сообщений

В `day7` окно измерялось сообщениями: `HISTORY_LIMIT = 20`. Но 20 коротких реплик и 20 длинных — это разные деньги, а платят именно за токены, поэтому в `day8` окно набирается под бюджет `CONTEXT_BUDGET = 4000`. Правило из `day7` осталось: окно набирается с конца и не начинается с ответа ассистента.

Ограничений теперь два, и они разной природы:

- **бюджет** — политика агента, мягкая: он про вход (system prompt, окно, вопрос) и не включает `max_tokens`. Один длинный вопрос может не влезть в бюджет целиком — обрезать историю дальше некуда, и запрос всё равно уходит, помеченный как перерасход;
- **лимит модели** — физика, жёсткая: `MODEL_CONTEXT_LIMIT = 1 048 576` токенов на вход и выход вместе. Если оценка запроса плюс `max_tokens` не влезает, агент не идёт в API, а сразу отдаёт ошибку.

Бюджет переключается в шапке (500, 2000, 4000, 16 000 токенов) и уходит вместе с запросом, так что окно пересчитывает сервер. На 500 токенах обрезка наступает через пару ходов — потерю памяти видно вживую.

### Как растут токены и стоимость

Вход растёт не потому, что растут вопросы, а потому что каждый ход тащит с собой всю предыдущую переписку: однострочный вопрос приезжает в модель вместе с 26 сообщениями контекста. За 20 ходов вход одного запроса вырос с 104 до 3006 токенов, то есть в 29 раз, при том что сами вопросы остались однострочными. Суммарно за диалог оплачено 35 848 входных токенов против 5457 выходных — платят в таком чате в основном за перечитывание собственной истории.

Стоимость хода при этом до 14-го хода почти не растёт — $0.000107 на первом, $0.000214 на четырнадцатом, — и держит её кэш префикса. Начало запроса от хода к ходу не меняется, DeepSeek отдаёт его из кэша блоками по 64 токена (128, 256, 384 … 2688 в таблице), а кэшированный вход стоит $0.007 за 1M против $0.22 — в 31 раз дешевле.

Дальше происходит самое интересное. На 15-м ходу окно упирается в бюджет, начинается обрезка — и кэш обнуляется: агент выбрасывает первые сообщения, начало запроса меняется, попадать в кэш больше нечему. Входная часть хода при том же объёме дорожает в 20 раз, с $0.000031 до $0.000634, а ход целиком — в четыре. Обрезка контекста экономит токены и одновременно ломает то, что делало их дешёвыми.

Тот же эффект виден в лоб, если прогнать один диалог на двух бюджетах (сценарий `memory`, 8 ходов):

| Бюджет | Вне контекста на последнем ходу | Стоимость диалога | Ответ на «как меня зовут?» |
| --- | --- | --- | --- |
| 4000 | 0 сообщ. | $0.000471 | «Игорь, Python.» |
| 500 | 10 сообщ. | $0.000639 | «Вы не сообщали своё имя или любимый язык в предыдущих сообщениях.» |

Экономный бюджет вышел на треть дороже щедрого и при этом потерял память: с шестого хода кэш обнуляется, а факт из первого хода уже выпал из окна. Обрезать контекст ради денег имеет смысл только выше порога, на котором префикс перестаёт попадать в кэш.

### Что ломается при переполнении

Ломается в четырёх разных местах, и только последнее выглядит как ошибка.

**1. Агент забывает начало диалога.** Самое тихое из всех: ответ приходит нормальным, `finish_reason: stop`, никаких предупреждений. Просто факт, названный в первом ходу, в окно уже не попал — и на прямой вопрос агент отвечает, что не знает. В интерфейсе это единственное, что о переполнении сообщает: счётчик контекста подсвечивается и пишет, сколько сообщений выпало.

**2. Ответ обрезается по `max_tokens`.** Лимит ответа в 2000 токенов — не лимит контекста, но упирается в него куда чаще. Модель останавливается с `finish_reason: length`, текст обрывается на полуслове. Под полем ввода появляется отметка об обрезке — иначе оборванный ответ выглядел бы как законченный. Проверка с `max_tokens: 32` на запросе «напиши конспект HTTP на две страницы» вернула ровно 32 токена ответа и оборвалась на «Объем рассчитан примерно на две».

**3. API отказывает до генерации.** Единственный настоящий отказ. Лимит `deepseek-v4-flash` — 1 048 576 токенов на вход и выход вместе, поэтому размер запроса сценарий подбирает не на глаз: сначала уходит калибровочный запрос, из его `usage` берётся точная цена одного блока текста (30.02 токена DeepSeek против 30 по `cl100k_base`), и уже от неё считается нужный объём.

Случай первый — сообщения не влезают сами по себе (5.34 МБ текста, 1 069 551 токен):

```
400 invalid_request_error
This model's maximum context length is 1048576 tokens. However, you requested
1068697 tokens (1068665 in the messages, 32 in the completion).
Please reduce the length of the messages or completion.
```

Случай второй — сообщения влезают, а вместе с запрошенным ответом нет: 700 003 токена в сообщениях плюс `max_tokens: 384000` (это максимум для V4) дают 1 083 425 против лимита:

```
400 invalid_request_error
This model's maximum context length is 1048576 tokens. However, you requested
1083425 tokens (699425 in the messages, 384000 in the completion).
Please reduce the length of the messages or completion.
```

Важное в этих ответах — не текст, а поведение: запрос отвергнут целиком, до генерации, ни одного токена не сгенерировано и не оплачено. Никакой частичной обработки нет: либо весь контекст влезает, либо ответа нет вообще.

**4. Агент отказывает раньше API.** Мёртвый запрос незачем гонять по сети: если оценка запроса плюс `max_tokens` не влезает в лимит, `ask()` бросает `ContextOverflow`, и на страницу уходит `event: error` с `kind: "overflow"` и числами. Вопрос на 1 160 113 токенов по оценке отваливается за 0.3 секунды — это локальная токенизация, до API дело не доходит.

Отклонённый запрос не тарифицируется: ни в двух отказах API, ни в отказе агента счёта нет. Если бы вход в миллион токенов всё-таки приняли, один только cache miss по прайсу flash стоил бы около $0.23 — в тридцать раз дороже всего двадцатиходового диалога из таблицы выше. Гигантский контекст не обязан ломаться — он может просто стоить как несколько сотен нормальных запросов.

### API

Счётчиков стало три: `history_size` и `history_tokens` — весь диалог в базе, `context_size` и `context_tokens` — окно, которое уйдёт в модель, и `context_budget` — на какой бюджет это окно набрано.

| Роут | Назначение |
| --- | --- |
| `GET /api/defaults` | system prompt, запрос по умолчанию, `model`, `temperature`, `max_tokens`, `context_budget`, `budget_options`, `model_context_limit`, `encoding`, прайс и признак пиковых тарифов |
| `POST /api/session` | создаёт сессию в базе, возвращает `{"session_id"}` |
| `GET /api/sessions` | `{"sessions": [{"id", "title", "size", "updated_at"}]}` — список диалогов для панели |
| `GET /api/session/{id}?context_budget=` | `{"history", "turns", ...счётчики}` — переписка и таблица токенов; окно считается на переданном бюджете |
| `DELETE /api/session/{id}` | удаляет сессию вместе с сообщениями и метриками, неизвестный `id` — `404` |
| `POST /api/ask` | `{"session_id", "prompt", "context_budget"}` → `text/event-stream` |

Кадров в потоке стало четыре:

| Кадр | Содержимое |
| --- | --- |
| `event: prompt` | числа до запроса: `question_tokens`, `request_tokens`, `dropped_messages`, `over_budget` и счётчики памяти |
| `data: <json-строка>` | часть ответа модели |
| `event: done` | факт: `prompt_tokens`, `cached_tokens`, `completion_tokens`, `cost_usd`, `estimated_tokens`, `drift_percent`, `finish_reason`, `word_count`, таблица `turns` и счётчики |
| `event: error` | `{"message", "kind"}`, где `kind` — `overflow` (не влезает в лимит модели), `api` (ошибка запроса) или `empty` (модель не вернула ответ) |

## day9 — сжатие истории

```bash
uvicorn main:app --reload --app-dir day9
```

Интерфейс доступен на http://127.0.0.1:8000

Тот же чат, что в `day8`, но переписку в запрос агент больше не тащит целиком: последние шесть реплик уходят дословно, а всё, что старше, он раз в десять сообщений пересказывает себе конспектом и дальше подставляет в запрос вместо самих реплик. Конспект виден на странице: под таблицей токенов появился блок «Конспект вместо истории», а в шапке — галочка «сжатие истории», которой тот же диалог можно провести на полной истории и сравнить ответы со счётом.

### Три части памяти

| Что | Где лежит | Что с этим в запросе |
| --- | --- | --- |
| Вся переписка | таблица `messages` | целиком не уходит в модель никогда |
| Конспект свёрнутой части | таблица `summaries`, действующий — последняя строка | системное сообщение перед хвостом |
| Хвост диалога | те же `messages`, последние `TAIL_MESSAGES` | дословно, как в `day8` |

Запрос собирается из четырёх частей, и только вторая — новая:

```
system: Ты — вежливый и краткий ассистент. ...
system: Краткое содержание предыдущей части диалога: <конспект>
user/assistant: последние 6 реплик дословно
user: новый вопрос
```

Конспект приходит системным сообщением, а не репликой ассистента: это не то, что кто-то сказал, а справка о том, что было до видимой части диалога. В `SYSTEM_PROMPT` об этом сказано прямо — «начало давнего разговора может прийти не репликами, а кратким содержанием», — иначе модель принимает конспект за чужой текст и начинает его комментировать.

### Политика: хвост, блок, конспект

Вся политика — четыре числа в [day9/memory.py](day9/memory.py):

| Константа | Значение | Почему так |
| --- | --- | --- |
| `TAIL_MESSAGES` | 6 | три последних хода — та часть разговора, где важны формулировки: «а подробнее?» относится именно к ним |
| `COMPRESS_EVERY` | 10 | свёртка платная, поэтому она не на каждом ходу, а раз в пять ходов — когда за хвостом накопился блок из десяти реплик |
| `SUMMARY_POINTS` | 18 | конспект пересказывает сам себя от свёртки к свёртке и без потолка растёт вместе с диалогом — ровно то, от чего мы уходим. Размер просят в тезисах, а не в словах: счёт строк модель выдерживает, счёт слов — нет |
| `SUMMARY_MAX_TOKENS` | 700 | жёсткий потолок конспекта: просьбу можно проигнорировать, лимит ответа — нет |

Свёртка инкрементальная: в модель уходит предыдущий конспект плюс новый блок реплик, обратно приходит один текст, который заменяет и то и другое. Блок отдаётся не диалогом, а расшифровкой (`Пользователь: ...` / `Ассистент: ...`) — получив чат, модель продолжает разговор, а нужен текст о разговоре.

Границу свёрнутого держит `covered_id` — id последней попавшей в конспект реплики. Поэтому агент не перечитывает базу после каждого хода: `Memory.live()` отбирает реплики новее этой границы, а `Memory.block()` — те из них, что вышли за хвост.

Бюджет контекста из `day8` остался, но сменил роль: основной объём убирает свёртка, а бюджет ловит случай, когда и хвоста слишком много. Проверка `ContextOverflow` не тронута — лимит модели по-прежнему физика, которую нельзя превысить.

### Свёртка — тоже запрос к модели

Два решения, которые видно в интерфейсе.

**Свёртка идёт после ответа, а не перед ним.** Пользователь уже читает реплику, пока агент пересказывает себе старое; ждать приходится только итоговых чисел хода. Если бы свёртка шла до запроса, каждый пятый ход начинался бы с полутора секунд тишины.

**Цена свёртки стоит отдельной строкой.** В таблице ходов у неё своя строка `свёртка` рядом со строкой `заголовок` из `day8` — обе пишутся в `turns` с `kind`, отличным от `turn`. Иначе экономия на ходах выглядела бы бесплатной, хотя платить за неё приходится сразу.

Неудачная свёртка ничего не ломает: конспект остаётся прежним, блок никуда не делся и уйдёт в модель на следующем ходу вместе с новыми репликами.

| Стоимость свёрток | $0.000000 | $0.002554 | — |
| Всего со служебными запросами | $0.002489 | $0.005976 | +140.1% |

Сжатие сэкономило четверть входных токенов и при этом вышло в 2.4 раза дороже. Виноваты две вещи, и обе — из `day8`.

**Свёртка платит за вход выходом.** Четыре свёртки — это 7940 токенов, и почти треть из них выходные, а выход стоит $0.66 за 1M против $0.22 за вход и $0.007 за кэш. Пересказ сорока реплик обошёлся в $0.002554 — дороже, чем весь сжатый диалог из 25 ходов.

**Сжатие выбивает запрос из кэша.** У полной истории начало запроса не меняется никогда, поэтому 86% входа приходит из кэша по цене в 31 раз ниже. Каждая свёртка меняет системное сообщение с конспектом, то есть самое начало запроса, — и следующий ход платит за вход полную цену. Это видно в таблице по ходам: ходы 9, 14 и 19 со сжатием стоят в два-три раза дороже своих двойников без сжатия, хотя токенов в них меньше.

Строка «вход по цене без кэша» показывает, сколько сжатие стоило бы само по себе, без второго эффекта: ровно те же −24%, что и в токенах. То есть сжатие работает как обещано, просто на этой длине диалога его выгода меньше, чем выгода от кэша, который оно ломает. Оно начинает окупаться там, где кэша нет или где важны не деньги, а лимит контекста: полная история растёт без предела, а конспект с хвостом — нет.

#### Качество ответов

Контрольные вопросы задаются после двадцатого хода, когда факты из первых реплик у сжатого агента остались только в конспекте. Ответы сверяет с эталоном модель-судья: 2 — все факты названы, 1 — часть потеряна, 0 — фактов нет.

| Вопрос | Без сжатия | Со сжатием | Ответ со сжатием |
| --- | --- | --- | --- |
| Как меня зовут и в каком сервисе я работаю? | 2 | 2 | «Тебя зовут Игорь, ты тимлид сервиса доставки еды «Тарелка».» |
| Перечисли наш стек: язык, фреймворк, база, очереди. | 2 | 2 | «Python и FastAPI, PostgreSQL 16, RabbitMQ.» |
| Каких провайдеров подключаем и как назвали адаптер и его методы? | 2 | 2 | «Провайдеры — Stripe и ЮKassa. Адаптер — `PaymentGateway` с методами `charge` и `refund`…» |
| Сколько лет храним историю платежей и почему? | 2 | 2 | «Пять лет — это требование юристов.» |
| Что решили про ключ идемпотентности и место платежей в архитектуре? | 2 | 2 | «Ключ идемпотентности — UUID v7… Платежи остаются в монолите отдельным модулем…» |

10 из 10 против 10 из 10: на этих вопросах сжатый агент не отличается от агента с полной историей. Но так стало не сразу.

#### Чего стоило качество: четыре версии промпта свёртки

Первая версия промпта просила «сохраняй факты, имена, числа и решения» и укладываться в 120 слов. Результат — 3 балла из 10: конспект добросовестно пересказывал последний блок реплик и терял всё, что было до него. Имя пользователя, названное в первом ходу, к четвёртой свёртке исчезало, и агент отвечал «в этом диалоге ты не называл своего имени» — при том, что в первой свёртке имя было.

| Промпт свёртки | Качество | Вход | Размер конспекта |
| --- | --- | --- | --- |
| свободный пересказ, «не длиннее 120 слов» | 3 из 10 | -44.3% | 381 → 400 ток., не растёт |
| четыре раздела, «факты и решения переноси все» | 9 из 10 | -21.9% | 498 → 946 ток., обрыв по `max_tokens` |
| то же плюс «не больше 18 тезисов» | 9 из 10 | -29.0% | 640 → 888 ток., обрыв по `max_tokens` |
| плюс «решения от свежих к старым» и уборка обрывка | 10 из 10 | -24.1% | 379 → 854 ток., плато у потолка |

Прогоны не повторяются токен в токен — ответы модели каждый раз разной длины, — поэтому сравнивать можно только внутри одного прогона: обе колонки каждой строки получены в одном запуске.

Из таблицы видно, чем на самом деле управляет промпт свёртки. Экономия и память тянут в разные стороны: чем короче конспект, тем больше экономия и тем быстрее из него выпадают старые факты. Полезными оказались три вещи:

- **разделы вместо свободного пересказа.** «Факты / Решения / Обсуждалось / Открыто» с требованием переносить факты и решения целиком — это и подняло качество с 3 до 9. Модель перестала выбирать, что важнее: у фактов теперь есть своё место, которое нельзя не заполнить;
- **лимит в тезисах, а не в словах.** «Не длиннее 120 слов» модель игнорировала, «не больше 18 тезисов, каждый не длиннее 12 слов» — выдерживала заметно лучше. Конспект всё равно упирался в `max_tokens`, но перестал раздуваться вдвое за свёртку;
- **порядок внутри раздела.** Пока решения писались от старых к свежим, обрыв по лимиту съедал самые свежие: в третьей версии агент забыл только что принятое решение оставить платежи в монолите. Переворот порядка отдал обрыву самые старые тезисы — и это последний балл из десяти.

Обрыв по лимиту всё равно остаётся: на сороковом сообщении конспект выходит на потолок `SUMMARY_MAX_TOKENS` и обрезается. Оборванный тезис не попадает в память — `tidy()` выбрасывает последнюю незаконченную строку, потому что недоговорённый факт в памяти хуже отсутствующего.

#### Что агент помнит вместо истории

Так выглядит первая свёртка — десять реплик в 379 токенах:

```
Факты:
- Игорь — тимлид сервиса доставки еды «Тарелка».
- Бэкенд на Python и FastAPI.
- База — PostgreSQL 16, очереди на RabbitMQ.
- Провайдеры: Stripe, подключают ещё ЮKassa.
- Таблицу платежей назвали payments.
Решения:
- Адаптер PaymentGateway с методами charge и refund.
- Абстрактный интерфейс PaymentProvider и реализации StripeProvider, YooKassaProvider.
- Выбор провайдера через фабрику или конфиг, домен независим от SDK.
- Вебхуки — отдельные эндпоинты, нормализация в общие события.
- Статусы фиксировать в БД до публикации события в RabbitMQ.
Обсуждалось:

- Поля запроса charge и колонки таблицы payments.
```

Каждая такая свёртка — отдельный запрос, и вот его цена (числа из сценария `summary`, который проигрывает тот же диалог только в сжатом режиме):

| Свёртка | Свёрнуто сообщ. | Вход | Ответ | Стоимость |
| --- | --- | --- | --- | --- |
| 1 | 10 | 1036 | 316 | $0.000382 |
| 2 | 10 | 1278 | 562 | $0.000598 |

Выход — 29% токенов и почти две трети цены: платит за сжатие именно он. Свёртки 3 и 4 упёрлись в `SUMMARY_MAX_TOKENS = 700` ровно, то есть конспект хотел быть длиннее, чем ему позволено.

Дальше конспект пересказывает сам себя: 379 → 642 → 854 → 854 токена. Раздел «Факты» за четыре свёртки только накапливался — имя, стек, пять лет хранения, ключ идемпотентности, Grafana с Prometheus дошли до конца диалога. Раздел «Обсуждалось» сжимался и к четвёртой свёртке был отрезан лимитом целиком. Это и есть работающая иерархия: факты дороже тем, решения дороже подробностей.

### API

К счётчикам памяти из `day8` добавились три: `summary_size` и `summary_tokens` — сколько реплик свёрнуто и во сколько токенов это встало, `pending_size` — сколько реплик ждёт следующей свёртки. Флаг `compression` ходит и в запросе, и в ответе: страница и сервер должны считать окно одинаково.

| Роут | Назначение |
| --- | --- |
| `GET /api/defaults` | к параметрам из `day8` добавились `compression`, `tail_messages`, `compress_every`, `summary_max_tokens` |
| `POST /api/session` | создаёт сессию в базе, возвращает `{"session_id"}` |
| `GET /api/sessions` | `{"sessions": [{"id", "title", "size", "updated_at"}]}` — список диалогов для панели |
| `GET /api/session/{id}?context_budget=&compression=` | `{"history", "turns", "summary", ...счётчики}` — переписка, таблица токенов и действующий конспект |
| `DELETE /api/session/{id}` | удаляет сессию вместе с сообщениями, метриками и конспектами, неизвестный `id` — `404` |
| `POST /api/ask` | `{"session_id", "prompt", "context_budget", "compression"}` → `text/event-stream` |

Кадров в потоке стало пять:

| Кадр | Содержимое |
| --- | --- |
| `event: prompt` | числа до запроса: `question_tokens`, `request_tokens`, `dropped_messages`, `over_budget` и счётчики памяти |
| `data: <json-строка>` | часть ответа модели |
| `event: compaction` | свёртка после ответа: `messages`, `summary_size`, `summary_tokens`, `replaced_tokens` и свой счёт |
| `event: done` | факт хода: токены, стоимость, `drift_percent`, `finish_reason`, `word_count`, таблица `turns`, текст конспекта и счётчики |
| `event: error` | `{"message", "kind"}`, где `kind` — `overflow`, `api` или `empty` |
