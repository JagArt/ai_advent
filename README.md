| [day16/](day16/README.md) | Веб-интерфейс: свой MCP-сервер по этому же репозиторию и клиент к нему — рукопожатие, список инструментов и один вопрос, уходящий в модель с инструментами и без них |

| [day20/](day20/README.md) | Веб-интерфейс: реестр трёх MCP-серверов — git, документация и хранилище — под одним каталогом с именами вида `docs__search`; длинный флоу на семь шагов идёт по всем трём серверам, данные между ними едут ссылками на артефакты оркестратора, а порядок вызовов сверяется с контрактом — и когда флоу ведёт код, и когда его ведёт модель |

| [day22/](day22/README.md) | Веб-интерфейс: первый RAG-запрос — вопрос идёт в поиск, найденные чанки пронумерованным блоком пристёгиваются к вопросу, и тот же вопрос уходит к той же модели без контекста; три ретривера сравниваются на эталонных отрывках day21, а качество ответов — на десяти контрольных вопросах, написанных руками, с обязательными фактами, ожидаемыми источниками и моделью-судьёй |
| [day23/](day23/README.md) | Веб-интерфейс: второй этап RAG — вопрос можно переписать, пул из двадцати кандидатов переставляется и режется по порогу, в промпт едет top-5; три переписывания и четыре реранкера сравниваются матрицей на эталонных отрывках day21, качество ответов — на тех же десяти контрольных вопросах в пяти режимах |
| [day24/](day24/README.md) | Веб-интерфейс: ответ обязан быть разложен на утверждения, у каждого — источник и дословная цитата из найденного чанка; цитата сверяется с чанком посимвольно, а судья-сверщик отдельно проверяет, что утверждение следует из своей цитаты; при слабом контексте работает двухслойный отказ — порог релевантности в коде до вызова модели и правило `unknown` в промпте, и отказ приходит вместе с уточняющим вопросом |
| [day25/](day25/README.md) | Веб-чат: мини-чат с RAG поверх формы day24 — история диалога в SQLite, ссылочная реплика разрешается в самостоятельный поисковый вопрос до поиска, а память задачи отдельным вызовом модели после каждого хода копит цель, ограничения и термины, причём сменить цель модель может только с объяснением, и проверяет это код; два сценария по 14 и 13 реплик прогоняются в трёх режимах памяти — без неё, только история, история с памятью задачи |

## Установка

Общее виртуальное окружение в корне, зависимости — под конкретный день:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r day2/requirements.txt
```

Зависимости `day2`–`day7` и `day11`–`day15` совпадают, в `day8`–`day10` к ним добавляется `tiktoken` — им считаются токены до отправки запроса, в `day16`–`day20` — `mcp`, SDK протокола. У `day21`–`day25` набор свой и общий: `mcp` там не нужен, зато нужны `model2vec` и `numpy` для эмбеддингов и `pypdf` для PDF.

Модель эмбеддингов `day21`–`day25` скачивается сама при первом запуске — 512 МБ в `~/.cache/huggingface`, дальше всё работает офлайн. Она локальная не из принципа: ни DeepSeek, ни OpenRouter эндпоинта эмбеддингов не дают.

## Настройка

Скопируйте `.env.example` в `.env` и укажите ключи:

```
DEEPSEEK_API_KEY=sk-xxxxxxxxxxxxxxxx
DEEPSEEK_MODEL=deepseek-v4-flash
OPENROUTER_API_KEY=sk-or-v1-xxxxxxxxxxxxxxxx
```

`.env` лежит в корне и подхватывается из папок day1–day25. `DEEPSEEK_MODEL` необязателен и читается в `day2`–`day4` и `day6`–`day25`, по умолчанию используется `deepseek-v4-flash`; в `day1` модель задана в коде, в `day5` — список моделей.

`OPENROUTER_API_KEY` нужен только в `day5`: слабая модель берётся из OpenRouter, потому что DeepSeek API отдаёт всего два уровня — `deepseek-v4-flash` и `deepseek-v4-pro`.

## Запуск

Команды рассчитаны на запуск из корня проекта, с активированным `.venv`.

`day1` — скрипт в терминале:

```bash
python day1/main.py
```

`day2`–`day26` — веб-интерфейс на FastAPI, команда одна и та же, меняется только папка:

```bash
uvicorn main:app --reload --app-dir day15
```

Интерфейс доступен на http://127.0.0.1:8000, а в `day10` рядом с чатом есть http://127.0.0.1:8000/scenarios — замеры стратегий кнопкой, с готовым markdown для README.

Замеры `day9` и `day11`–`day15` запускаются скриптом, а не из браузера, — вывод сразу в markdown:

```bash
python day15/scenarios.py
```

В `day16` и `day17` из терминала запускается сам MCP-клиент — соединение и список инструментов, без веба и без ключей. В `day17` клиент ещё вызывает `git_log` и печатает результат:

```bash
python day17/client.py
```

В `day18` MCP-сервер — отдельный постоянный процесс с планировщиком, его запускают первым, в своём терминале; веб-интерфейс и клиент подключаются к нему по HTTP:

```bash
python day18/server.py                      # MCP-сервер и планировщик, http://127.0.0.1:8765/mcp
uvicorn main:app --reload --app-dir day18   # веб-агент и лента сводок
python day18/client.py                      # расписание и сводка за час, без веба и без ключей
```

В `day19` сервер снова stdio-подпроцесс, отдельно его запускать не нужно. Клиент из терминала проходит цепочку целиком, и ключ ему нужен: сводку делает модель внутри сервера.

```bash
uvicorn main:app --reload --app-dir day19   # страница с пайплайном и чатом
python day19/client.py                      # search → summarize → save_to_file одним вызовом
```

В `day20` серверов три, и транспорты у них разные. Постоянное хранилище запускают первым, в своём терминале; серверы `git` и `docs` поднимаются подпроцессами сами. Клиент из терминала проходит весь длинный флоу, и ключ ему нужен — тезисы делает модель внутри сервера `docs`:

```bash
python day20/servers/vault.py               # постоянный MCP-сервер хранилища, http://127.0.0.1:8770/mcp
uvicorn main:app --reload --app-dir day20   # страница с реестром, флоу и чатом
python day20/client.py                      # семь шагов по трём серверам и проверка порядка
```

Тему отчёта можно передать клиенту аргументом: `python day20/client.py "артефакты и пайплайн day19"`.

В `day21` модели и сети нет вовсе, кроме одного шага: эмбеддинги считаются на машине, поиск — перебором на numpy. Страница поднимается как обычно, а индексы собираются кнопкой или из терминала:

```bash
uvicorn main:app --reload --app-dir day21   # корпус, индексы, поиск, сравнение стратегий
python day21/scenarios.py                   # корпус, сборка трёх индексов и сравнение в markdown
python day21/scenarios.py search "инкрементальная переиндексация по sha файла"
```

Ключ в `day21` нужен только шагу, который придумывает пробы для сравнения, — его результат лежит в `day21/probes.json` и коммитится, поэтому заново запускать шаг не обязательно:

```bash
python day21/scenarios.py probes            # 120 проб по случайным отрывкам корпуса
```

PDF и статьи для индексации кладутся в `day21/corpus/` — пайплайн подхватывает их сам. Отсканированный PDF без текстового слоя он не молча пропустит, а назовёт причину.

`day22` берёт индекс day21 и достаёт из него ответ. Страница задаёт вопрос сразу в двух режимах — с найденным контекстом и без него, — а из терминала прогоняется и сравнение ретриверов, и контрольный набор:

```bash
uvicorn main:app --reload --app-dir day22   # вопрос в двух режимах, контекст, замеры
python day22/scenarios.py                   # индекс, ретриверы и контрольный набор целиком
python day22/scenarios.py ask "Зачем проекту ключ OpenRouter?"
```

Индекс `day22` свой и собирается отдельно — он не делится с day21, потому что папку day22 из корпуса приходится исключать. Ключ нужен только шагам `ask` и `questions`: сборка, сверка набора и сравнение ретриверов считаются на машине.

`day23` ставит второй этап между поиском и ответом. Страница задаёт вопрос сразу в пяти режимах — без базы, как в day22, с переписыванием, с фильтром и с обоими, — а из терминала прогоняются матрица режимов, развертка по порогу и тот же контрольный набор:

```bash
uvicorn main:app --reload --app-dir day23   # пять режимов, дошло / отсеяно, матрица, развертка
python day23/scenarios.py                   # индекс, матрица и контрольный набор целиком
python day23/scenarios.py ask "На каком порту слушает постоянный MCP-сервер хранилища в day20?"
python day23/scenarios.py matrix            # 3 переписывания × 4 реранкера на 119 пробах
python day23/scenarios.py sweep             # развертка по порогу отсечения
```

Индекс `day23` свой: из корпуса исключены и своя папка, и day22, иначе поиск находил бы разбор контрольных вопросов вместе с ответами. Кэши `rewrites.json` и `relevance.json` коммитятся — без них матрица стоит сотни вызовов модели. Ключ нужен `rewrite`, `rerank`, `ask` и `questions`; `matrix` и `sweep` после прогрева считаются на машине.

`day24` берёт конвейер day23 без изменений и меняет только форму ответа: модель обязана разложить его на утверждения, у каждого назвать источник и привести дословную цитату, а при слабом контексте отказаться и попросить уточнение. Страница показывает четыре режима рядом, с отметкой сверки у каждой цитаты:

```bash
uvicorn main:app --reload --app-dir day24   # четыре режима, цитаты со сверкой, отказы
python day24/scenarios.py                   # индекс, набор, цитаты, слабый контекст целиком
python day24/scenarios.py ask "На каком порту слушает постоянный MCP-сервер хранилища в day20?"
python day24/scenarios.py quotes            # разбор всех цитат набора: что нашлось дословно
python day24/scenarios.py quotes --runs 12  # то же на двенадцати прогонах: ловит редкую выдумку
python day24/scenarios.py weak              # восемь вопросов слабого контекста: отказы и уточнения
python day24/scenarios.py gate              # развертка по порогу отказа
```

Индекс `day24` тоже свой, и из корпуса выброшены уже три папки: своя, day22 и day23 — README обеих разбирают контрольные вопросы вместе с ответами. Множество документов при этом остаётся прежним, поэтому кэши `rewrites.json` и `relevance.json` переехали из day23 горячими: их подписи считаются по тексту, а не по идентификаторам чанков.

`day25` превращает одиночный вопрос day24 в разговор: история диалога, разрешение ссылочных реплик до поиска и память задачи — цель, ограничения и термины — отдельным вызовом модели после каждого хода. Страница слева чат, справа память задачи с подсветкой того, что изменилось ходом:

```bash
uvicorn main:app --reload --app-dir day25   # чат, память задачи, строка «искали по», сценарии
python day25/scenarios.py                   # корпус, индекс, оба сценария в трёх режимах, развертка
python day25/scenarios.py chat              # живой диалог в терминале, с источниками и памятью
python day25/scenarios.py dialog memory     # один сценарий ход за ходом: что переписали, что нашли
python day25/scenarios.py goal              # удержание цели: журнал формулировок и сверка с исходной
python day25/scenarios.py sweep             # развертка по порогу отказа на сценарии
```

Диалоги и память лежат в `day25/chat.db` и переживают перезапуск, индекс — свой, с четырьмя исключёнными папками: к day22 и day23 добавился day24. Полный прогон стоит около 160 вызовов модели: 27 ходов × 3 режима, и на каждом ходу с памятью ещё разрешение ссылки и обновление состояния, плюс судья. Три режима памяти сравниваются там же, но на двух сценариях разброс между прогонами перекрывает разницу между режимами — почему так, разобрано в [day25/README.md](day25/README.md).

`day26` уходит от облака: модель — `qwen3-4b` в [LM Studio](https://lmstudio.ai), ключи не нужны, зависимости те же, что в `day2`. Сервер LM Studio запускают первым; адрес и модель меняются переменными `LMSTUDIO_BASE_URL` и `LMSTUDIO_MODEL`, по умолчанию `http://localhost:1234/v1` и `qwen3-4b`:

```bash
lms server start                            # сервер LM Studio, http://localhost:1234/v1
lms load qwen3-4b                           # если модель ещё не загружена
uvicorn main:app --reload --app-dir day26   # статус сервера, три запроса, рассуждения и замеры
python day26/scenarios.py                   # три запроса в двух режимах, вывод в markdown
```
